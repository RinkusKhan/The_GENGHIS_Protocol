# Changelog

_What changed and when. **Why** lives in [DECISIONS.md](DECISIONS.md) (D-numbers); **where we are** in
STATUS.md. Newest first. Dates are the day the change landed on `main`._

## 2026-10-03
- **D58 — a chat goes to the box that runs its model clearly faster.** A box used to run any model that fit its own
  card there, even when another box ran it far faster on its own (Qwen3-Coder-30B: 763 s to the first token on an Intel
  Arc iGPU, 13.7 s on a 5090). Now a box hands the chat to a host whose card is at least 2x faster, judged by each card's
  measured GB/s, a figure that compares cards whatever model ran (tokens/s x bytes read per token). Every answer refines
  it; `fleet bench` measures every GPU at once; the Fleet table shows it. A cold hand-over happens only if that box loads
  the model within 60 s (each box learns its folders' load speed); otherwise the chat is answered here and the faster
  box loads it in the background for the next one. Lend off keeps a GPU out; a model placed on a card stays there.
- **A host's own settings are set on the host.** `models_dirs`, `residency`, `resident_ctx` and `resident_kv` sent to
  a host's `POST /config` used to be forwarded to the authority and set there instead.
- **Fix: a model could not be placed on a chosen card of a box with two GPUs (D57).** Since an eGPU joined a box's own
  card (D46), putting a model on either card from the Control Room or a formation failed with "too big for this host's
  card (needs ~11 GB, ~21 GB usable)". The request was planned for the whole box (which picked the faster eGPU over
  loopback), and the warm step accepted only a plan on the host's own card; a refusal for the named card was also
  overwritten by that whole-box answer. A warm is now planned for the card that was chosen, an eGPU (no serve of its own)
  is handled by the host in its box (from any host's Control Room), the card's name travels on every forward, and asking
  for a model that is already warm there says so.
- **Fix: a warm model whose card's donor restarted stayed "already warm" while its server was dead.** A warm request now
  checks the server answers; a dead one is dropped and the model is warmed afresh.
- **Fix: `verify`'s `launcher` check warned about a healthy Linux donor** after it was restarted from its `@reboot` line:
  it matched the `sh -c` wrapper, whose command line names `ggml-rpc-server`. It now judges the program that runs.
- **Roles are labelled experimental** in the README and USAGE: the fleet-pooling core is the proven part.
- **Fix: three scripts damaged by escape mangling.** `donor-report.sh`'s mDNS fallback had a raw 0x01 byte where `sed`'s
  `\1` belonged (a donor without `GENGHIS_COORD` never found the authority); `run-client.ps1` did not parse in Windows
  PowerShell 5.1 (an em dash in a file without a byte-order mark); the error line a failed chat shows (`engine_error`) had
  two literal backspaces in its pattern, so it never matched. A sweep of every shipped text file for control bytes is now
  part of the release check.

## 2026-10-01
- **The serve keeps answering when its launcher dies.** The serve's output is a pipe to its launcher; once the launcher
  was gone, every log line raised inside the request handler and the reply was dropped ("connection closed"). Writes to a
  dead pipe are now dropped instead.
- **`verify` has a `launcher` check:** a serve or a donor still running after its launcher died (no restart after a crash,
  nothing reaches its log) is a WARN, with the PID and how to restart it under its launcher.
- **The donor's tensor cache has a cap.** `ggml-rpc-server -c` keeps every tensor it was ever sent and never removes one
  (52 GB in two weeks on one donor). Both donor launchers now prune it to `GENGHIS_RPC_CACHE_GB` (default 30), least
  recently used first, and harder while the disk is under 10 % free.
- **Service cards take a `"log"` file (D56).** On Windows a service is started detached, and a `cmd /c ... > file`
  redirect inside its command wrote nothing; the serve now opens the file and hands it over.

## 2026-09-30
- **Fix: a long request to a model split across cards failed with the engine's raw error.** A model too big for any one card, and not kept warm, runs as a one-off engine, and that engine always started with a 4,096-token context. Anything longer (a pasted document, a long chat, a coding tool's instructions: 5-9k tokens) came back as "request (5806 tokens) exceeds the available context size (4096 tokens)". The engine's context is now sized to the request, the same way warm servers are sized (a step above the request, within what the model was trained for and what the cards in the split have left), and the status says what it chose. When the request really cannot fit, the answer says so and why before a long load. Found by pointing a coding agent (Aider) at GENGHIS's /v1 API.

## 2026-09-28
- **OpenCV and scikit-image work in the Code Interpreter.** Open WebUI's own copy of Pyodide lists ~250 packages but ships the files of ~50, so the first real photo repair failed on `import cv2` ("Failed to fetch") although GENGHIS tells the model it can use it. `provision.py` now fetches the packages GENGHIS promises (OpenCV, scikit-image and their dependencies, ~22 MB) from Pyodide's CDN for exactly the chat UI's build, checks each against the checksum in Pyodide's own package list, and puts them where the browser looks; the watchdog's run heals a recreated container. A browser tab that already failed to load one needs a reload.
- **"It didn't write":** it did; the Files panel does not refresh itself after the code saves a file. The model now says the file's name and to press the panel's refresh button.

## 2026-09-26
- **D56 — home services: start and stop a program from the Control Room, and a GPU has one owner at a time.** A file in `<home>/services/` on the box that runs it (start and stop commands, an address that answers while it runs, a link to open) becomes a card next to the local resources on every host's Control Room. With `"gpu": true` the card takes that GPU out of the pool while the program runs: nothing is planned, handed over or warmed onto it, pooled shards there are reclaimed, and the Fleet table shows HELD. Start refuses while GENGHIS holds a model on that box and asks before unloading it; a program started or stopped some other way is noticed within 15 s; a stop only counts once the program has exited. Example: `home.example/services/example.json.example` (not loaded until renamed).
- **The Coder and Researcher work on the files you give them in the chat.** Pick the role, drop files into Open WebUI's Files panel, ask; the model writes Python, your browser runs it (the Code Interpreter), results land back in the Files panel. What it took, all found by testing the real chat end to end: `provision.py` gives every role Open WebUI's plain ("legacy") calling with the Code Interpreter on by default (in 0.11 an unset mode means native, where the interpreter is a builtin tool GENGHIS keeps off, so it never arrived); GENGHIS stops telling a model "you cannot read files" when the interpreter is in the conversation, merges every system instruction into one, and says the exact run tag first; a ```python block (or a tag without `type="code"`, which Open WebUI shows but never runs) is turned into a runnable block as it streams; and a run's output is handed back as a turn to answer, not a half-written answer to continue (the model had redone the whole task five times). Coder-14B is the Coder's first choice on the NUC (fits the 5060 Ti on its own).
- **Fix: a swap away from a model server the serve re-adopted after a restart knocked the card's rpc-server over.** Adopted servers are now waited for before the next starts, and a server whose RPC device is briefly missing (rpc-server restarting) is started once more.
- **D55 — roles that act on a workstation.** Two new adapter transports. `mcp` plugs in any Model Context Protocol tool server (Visual Studio's first) and offers the model only the tools the file's `allow` list names. `files` is built in: list, read, find and search inside the folders its `roots` name (symlinks and `..` cannot leave; key and credential files are never opened); with `"write": true`, every write keeps the previous version in `.genghis-backup/` and the chat shows the diff; no delete. A role that mixes web and local access is warned about in the chat; a role can set `max_rounds` (up to 24) for build-fix loops. Example files `home.example/adapters/files.json` and `visualstudio.json` ship switched off. **The Coder workspace** (Control Room card): one root you point anywhere (`D:\Coder`, or `F:\Project` for a USB session) with recent roots one click away, a project folder inside it (or the whole root, or a new one), and the two switches; the Coder sees only the project, backups stay inside it; system, profile, key and GENGHIS-home folders are refused as a root; changed on any host's Control Room, saved on the box that has the folders.
- **Fix: the Blender role "never responded".** Blender was closed, or the laptop's serve was down, and GENGHIS said so only in the NUC's log. The Thinking panel now shows the role and every warning about its tools, the Blender check says what to do, and adapters dial `127.0.0.1` for `localhost` (Windows tried IPv6 first and lost 2 s per call, enough for the relaying host to give up).
- **Fix: a second warm model on the same card over RPC waited forever.** llama.cpp's `rpc-server` serves one client at a time, and a warm server keeps its connection for life. After a reboot, the chat UI's title model (the 1.5B) warmed onto the NUC's eGPU over loopback; the 14B chat was then planned onto the same card and sat at "Loading model" (its connection unaccepted in the rpc-server's queue) while the Pool drew both as warm. Now: the planner plans around an RPC endpoint another warm model of this host holds, unless the new model is the bigger one, in which case it takes the card and the holder is unloaded first (said in the chat; a chosen placement is never moved and the refusal says why); that unload counts as an eviction, so the D38 hand-over sends the chat to a host that already has the model warm (the laptop had the 14B); and a load its RPC server never accepts fails after 3 minutes with the reason instead of "loading…" for 40. The Pool labels a card with every pooled model on it, not the first one found.

- **The authority's installer adds the watchdog** (every 15 min), and `verify` has a `watchdog` check. It used to be a manual step, so a newcomer's authority had no independent health pass, and Open WebUI on it was never set up for local models (its ~30 built-in tools stayed on, and a local model calls them instead of answering).

The projector now rides along (`--mmproj`), its memory is counted, and a warm server started without it is restarted with it. Tested: a generated two-colour picture described correctly in 17 s, restart included.

- **A fresh-box install test, and everything it found.** A fresh AI agent, given only the public repository and AGENTS.md, installed a clean Ubuntu 26.04.1 VM as a CPU donor. It finished (`verify` PASS; 29/29 layers on the VM at 19.0 t/s) and reported 14 friction points. Fixed:
  - **Two donor servers fought over one port.** The setup script started its own server in `tmux` while the installer started `donor-serve.sh`; the tmux copy won, unsupervised, and the loop failed to bind every 5 s. Now `donor-serve.sh` is the only launcher: one instance per port (a second copy says so and leaves), and it waits quietly, logging once a minute, if something else holds the port. The setup scripts serve through it, or start nothing when the installer calls them.   - **Ages across timezones.** The authority writes timestamps in its own local time, so a box set to another timezone (the VM ran UTC; the authority EDT) read a node registered seconds earlier as "last seen 14401 s ago". The same flaw would have made a **host** in another timezone judge every shard booking and live report stale. The authority now sends its clock with `/fleet.json` (`X-Genghis-Now`), and every "how old is this?" (`verify`, booking and report freshness) measures against it.
  - **Preflight and the installer:**
    - The render/video group check now runs only for Vulkan. A CPU donor's `/dev/dri` is at most a display adapter, and with `--yes` the user would have been re-grouped for nothing.
    - With no terminal, a question used to get a silent "no"; it now prints a `[ ?? ]` line saying so and how to consent (`--yes`).
    - Preflight checks the authority answers, and notes when the box is on Wi-Fi.
    - New `--name` sets the box's fleet name, instead of `ubuntu`.
  - **`donor-setup-linux.sh`** installs only the build tools that are missing, says so, and no longer adds two packages it never used. **`donor-setup-cuda.sh`** follows D52 (below) and never installs Ubuntu's own CUDA toolkit.
  - **`verify`:**
    - Inside a virtual machine, the `link` check says INFO ("a VM's network card always looks wired") instead of claiming wired.
    - A node marked DOWN that answered under 3 minutes ago is a WARN, "probably busy: just benched?", instead of a FAIL pointing at the firewall.
    - The GPU and CUDA-toolkit checks follow D52.
    - The docs no longer call it "read-only" without saying it writes its address card.
  - **Version stamp:** a fresh copy of the repository reported `…·deployed` because every unpacked file looked newer than the date written in `BUILD`. It now compares file with file.
  - **`init`** no longer advises hand-editing `fleet.json`.
  - **Docs:** a real `git clone` URL; `add-a-box.md` no longer claims x86 boxes are proven (only as a VM so far); a note for agents running the installer without a terminal; VM and "just benched" notes in `when-verify-fails.md`.
- **D52 — NVIDIA support: RTX 20 / GTX 16-series and newer, on one toolkit; GTX 10-series experimental.** Every supported card builds with CUDA 13.2+ from NVIDIA's repository. The CUDA setup script refuses an older card with the reason (`GENGHIS_ALLOW_OLD_GPU=1` to try anyway), finds NVIDIA's `nvcc` off the default PATH, and stops with NVIDIA's exact commands if 13.2+ is missing. ## 2026-09-22
- **Docs and instructions caught up, and three fixes an agent or a new user would have hit.** (1) **The chat UI pin is `v0.11.4`**, the security release D47 says earns a bump: the reference instance was upgraded and tested on it, but the repository's `docker-compose.yml`, USAGE and INSTALL still pinned `v0.11.3`, so a fresh install would have got the version the advisory is about. (2) **`--preflight` / `-PreflightOnly` now really change nothing:** both installers' package helpers still offered to install (and with `--yes` / `-Yes`, *did* install) during preflight. That matters because AGENTS.md tells an agent that preflight is safe. (3) **"Restart the serve over SSH" instructions no longer kill your session or match nothing:** USAGE said `pkill -f 'genghis_coordinator.py serve'`, which matches the SSH shell itself, and INSTALL's anchored alternative `^/usr/bin/python3 genghis_…` missed the real `python3 -u …` process, so the serve silently never restarted. Both are now `pkill -f 'genghis_coordinator[.]py serve'` (the bracket can't match the shell's own command line), tested live. Also: `/v1` echoes a model asked for by name instead of relabelling it `genghis-balanced`. Docs: USAGE gains roles, attaching a document, and `verify`, and no longer points the model library at a Pi; README's status table lists roles, `verify`/AGENTS.md, the measured record and attachments; the command reference, INSTALL and the migration guide no longer describe the Pi as the authority or use Pi placeholders.
- **Fix: a `pip install --user pypdf` was invisible to a serve that was already running.** Python adds the per-user site folder (`%APPDATA%\Python\Python3xx\site-packages`) to its search path only if that folder *exists at startup*. The laptop's first `--user` install created it, so the running serve kept reporting "cannot read PDFs" after a successful install, and "no restart needed" wasn't true. The PDF check now adds that folder once it exists (when user site is enabled). Reproduced in isolation with the laptop's own Python 3.11 (folder absent at start → install mid-run → the same process reads the PDF), then confirmed live: `verify` PASS `pdf`, and an attached PDF answered from its contents in 0.6 s.
- **A document attached to a chat is read, not a 502.** An OpenAI-style `file` (or Responses `input_file`) content part carrying a PDF made the warm model server answer HTTP 400 "unsupported content[].type", and the user got a **502** instead of an answer. The per-request path silently dropped the file instead. Now the first host to receive a request turns each attached document into text before any model sees it: PDF page by page (with `pypdf`), text files as they are, at most about 40,000 characters per document with any cut stated. A document it can't read (no `pypdf`, a scanned PDF, an image or other type, an uploaded-file id) becomes a sentence telling the model, and so the user, why and how to fix it, and the Thinking panel lists what happened to each attachment. Tested with every case (PDF, scan, text, oversized, unknown type, `input_file`, no `pypdf`) and live on the laptop: the attachment that got a 502 now answers in 0.9 s. (Open WebUI already reads a dropped PDF inside its own container and sends text.)
- **The right Python.** On Windows, `py` can launch a *different* Python from the one the serve runs: the reference laptop's `py -m pip install pypdf` went into Python 3.13 while its serve runs 3.11, so nothing changed. Every "install pypdf" message now names the serve's own interpreter; the serve reports its interpreter and PDF ability in `/roles.json`; and `verify`'s new `pdf` check asks the running serve instead of judging from whichever Python launched `verify` (it warned correctly while launched under 3.13). The installers now offer `pypdf` on **every** box a person uses (every Windows install, and Linux authority, host and client), never on a donor, and install it into the same Python the serve launcher picks.
- **PDF reading is part of the install, on the boxes that need it.** Both installers now offer `pypdf` on a box that answers chats (the authority, or `--serve` / `-Serve`): `python3-pypdf` from the distro on Linux, `pip install --user pypdf` on Windows. It's announced and confirmed like every other install, only reported in preflight, and never offered to a donor, which never reads knowledge. `verify` gains a `knowledge` check that warns, with the exact command, when a role's folder has PDFs this box can't read, which also covers installs made before today. **Fix:** the knowledge index is now keyed on whether a PDF reader is available, so installing `pypdf` takes effect on the next question; before, a folder indexed without it kept calling every PDF unreadable until a file changed. Tested on the NUC with a real PDF (the same cached folder went from "1 PDF skipped" to citing `keeper.pdf, p.1` with no restart), and on the laptop, which lacks `pypdf` (`verify` warned with `py -m pip install pypdf`).
- **D50 BUILT — a role reads its knowledge folder.** A role's `knowledge` was declared and inert; now every request is searched against it (BM25 keyword retrieval, stdlib only, no embedding model, no index file) and up to 4 passages (~6,000 characters max), tagged `[K1]`…`[K4]` with file and page, go inside the role's system prompt. Text, Markdown, reST, CSV, JSON and HTML are read directly; PDFs need the optional `pypdf` (`sudo apt install python3-pypdf`). Anything it can't read is counted and named (in the request's note, `/roles.json` and `genghis roles <id>`), never skipped quietly. `genghis roles <id> "a question"` previews the passages. - **D49 BUILT — ADAPTERS: a role's tool belt now acts, and Blender is the first one.** D48 left the belt *declared*; this makes it real.
